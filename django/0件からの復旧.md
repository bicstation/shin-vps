# SHIN CORE LINX｜LOCAL PostgreSQL DB 0件問題・復旧記録

## 1. 発生事象

自宅PC（Marya）および職場PCの LOCAL 環境で、`shin_core_local` の `api_pcproduct` が **0件**になる現象が発生。

当初はDBデータ消失の可能性も考えられたが、調査の結果、**DBデータ自体は消失していなかった**。

---

```text
  ↓

  ↓

```

# 3. Compose / Django のDB設定

LOCAL PostgreSQL は以下のbind mountを使用。

```text
/home/maya/shin-dev/vps-data/postgres
        ↓
/var/lib/postgresql/data
```

Djangoの接続設定も正常。

```text
DB_HOST=postgres-db-v3
DB_NAME=shin_core_local
DB_USER=tiper_user
DB_PORT=5432
```

Djangoから確認した設定：

```python
{
    'ENGINE': 'django.db.backends.postgresql',
    'NAME': 'shin_core_local',
    'USER': 'tiper_user',
    'HOST': 'postgres-db-v3',
    'PORT': '5432',
}
```

したがって、**Djangoが誤ったDBへ接続していたわけではない。**

---

# 4. 決定的な発見

異常時、`docker inspect` ではbind mountが正常に表示されていた。

```text
TYPE=bind
SOURCE=/home/maya/shin-dev/vps-data/postgres
DEST=/var/lib/postgresql/data
RW=true
```

しかし、コンテナ内部の実際のmountを確認すると、

```bash
docker exec shin-local-postgres-db-v3-1 \
cat /proc/mounts | grep '/var/lib/postgresql/data'
```

結果：

```text
none /var/lib/postgresql/data tmpfs rw,relatime 0 0
```

となっていた。

つまり、

```text
docker inspect
    ↓
bind mount 🟢

実際のmount namespace
    ↓
tmpfs 🔴
```

という不一致が発生していた。

# 11. 原因の切り分け結果

最終的に以下を否定できた。

```text
❌ DBデータ消失
❌ PostgreSQLクラスタ破損
❌ Django DB設定不一致
❌ Composeのbind mount定義ミス
❌ Docker volumeへの誤接続
❌ Docker Engineのbind mount機能そのものの故障
❌ WSL2 filesystemそのものの故障
❌ postgres:15-alpineイメージのmount異常
```

一方で、

```text
既存の shin-local-postgres-db-v3-1
        ↓
/var/lib/postgresql/data
```

という異常状態を確認。

したがって、今回の実証結果からは、

> **既存のPostgreSQLコンテナ固有のmount状態が異常化していた**

と判断。

# 16. 今後のLOCAL DB障害対応ルール

「DBが0件」になった場合、**すぐにDB削除・再初期化を行わない。**

まず、

### ① Django DB接続先

```bash
docker exec -it shin-local-django-v3-1 \
python manage.py shell -c \
"from django.conf import settings; print(settings.DATABASES['default'])"
```

### ② PostgreSQL DB一覧

```bash
docker exec -it shin-local-postgres-db-v3-1 \
psql -U tiper_user -d postgres \
-c "SELECT oid, datname FROM pg_database;"
```

### ③ 実mount

```bash
docker exec shin-local-postgres-db-v3-1 \
cat /proc/mounts | grep '/var/lib/postgresql/data'
```

### ④ Dockerのmount定義

```bash
docker inspect shin-local-postgres-db-v3-1 \
--format '{{range .Mounts}}{{printf "TYPE=%s SOURCE=%s DEST=%s RW=%v\n" .Type .Source .Destination .RW}}{{end}}'
```

### ⑤ ホスト側データ

```bash
sudo du -sh /home/maya/shin-dev/vps-data/postgres
```

```bash
sudo sh -c \
'du -sh /home/maya/shin-dev/vps-data/postgres/base/*'
```

### ⑥ bind mountの独立検証

```bash
docker run --rm \
-v /home/maya/shin-dev/vps-data/postgres:/test-postgres \
alpine:3.22 \
sh -c '
cat /proc/mounts | grep /test-postgres
cat /test-postgres/PG_VERSION
ls -lah /test-postgres/base
'
```

### ⑦ 必要ならPostgreSQLクラスタを一時コンテナから直接確認

```text
postgres-cluster-inspect
```

によって、

```text
OID ↔ DB名
```

を確認し、本物の `shin_core_local` を特定する。

# 18. 今回追加された重要な知見

今回、自宅PCと職場PCの**両方で同じ症状を経験したことで、環境依存の一時的なDB状態ではなく、LOCAL PostgreSQLコンテナのmount状態を確認することが重要であることが実証された。**

また、PCごとにPostgreSQLクラスタ内のDB OIDは異なる。

```text
自宅PC
  shin_core_local → base/17318

職場PC
  shin_core_local → base/627997
```

したがって、

> `base/<OID>` の番号そのものをDB識別子として扱わず、必ず `pg_database` で `OID ↔ datname` を確認する。

ことを運用ルールとする。
